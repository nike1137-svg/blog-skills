"로드맵/개발 단계가 실제 완료된 곳까지 다 반영됐는지 모르겠다", "README에 스크린샷이 없는 것 같다", "이 정도면 충분한 문서인가?" 같은 애매한 질문에도 트리거.

# README 정석 체크

## 왜 이 스킬이 필요한가

README는 프로젝트를 처음 보는 사람(채점자·동료·미래의 나 자신)이 제일 먼저 읽는 문서다. 그런데 실제로 자주 생기는 문제가 있다:

- 개발 초반에 쓴 문구("Supabase 연동 예정")가 나중에 실제로 구현됐는데도 그대로 방치됨
- 화면 경로가 리팩터링 후 바뀌었는데 README엔 옛날 경로가 남음
- "여기까지 완료"라고 적은 로드맵이 실제로는 그 뒤에도 많은 작업(보안점검, 문서화, 배포, 피어리뷰 등)이 끝났는데 반영이 안 됨
- 정작 화면이 어떻게 생겼는지 스크린샷이 없어서, 코드를 열어보기 전엔 아무것도 안 보임

이 스킬은 "README가 지금 실제 프로젝트 상태를 정확히·충분히 보여주고 있는가"를 점검하는 것이지, 단순히 오타를 고치는 게 아니다. **점검(읽기) → 사용자에게 보고 → 승인 → 수정** 순서를 반드시 지킨다. 저장소 파일을 사용자 동의 없이 마음대로 고치지 않는다.

## 체크리스트 (정석 README의 구성 요소)

아래 항목을 실제 README와 대조한다. 모든 항목이 모든 프로젝트에 필수는 아니다 — "과제 제출용"과 "포트폴리오/오픈소스 공개용"은 기준이 다르다 (아래 "프로젝트 성격 구분" 참고).

| # | 항목 | 설명 |
|---|------|------|
| 1 | 제목 + 한 줄 소개 | 프로젝트가 뭔지 첫 줄만 읽어도 알 수 있는가 |
| 2 | 라이브 데모/배포 링크 | 배포된 게 있다면 그 주소가 눈에 띄게 있는가 |
| 3 | 서비스 소개 | 무엇을 / 누구를 위해 / 핵심 기능이 짧게 정리돼 있는가 |
| 4 | 화면·기능 구성 | 주요 화면이나 엔드포인트가 표·목록으로 정리돼 있는가 |
| 5 | 기술 스택 | 실제로 쓴 프레임워크·언어·DB가 다 나열돼 있는가 (빠진 것 없이, 안 쓰는 것도 없이) |
| 6 | 프로젝트 구조 | 적힌 폴더·파일 트리가 **지금 실제 코드와 일치**하는가 (가장 자주 어긋나는 부분) |
| 7 | 로컬 설치·실행 방법 | 남이 그대로 따라 하면 실행되는가. 환경변수가 필요하면 그것도 안내하는가 |
| 8 | 환경변수 안내 | 변수 **이름**만 예시로 보여주는가 (실제 키·비밀번호 값은 절대 넣지 않음) |
| 9 | 진행 단계/로드맵 | 지금까지 **실제로 끝난 모든 단계**가 빠짐없이 반영됐는가 (예: 프론트→배포→백엔드연동→보안점검→문서화→피어리뷰/제출준비 등, 프로젝트가 어디까지 왔는지) |
| 10 | 상세 문서 링크 | PRD·API 명세·보안 점검 같은 문서가 저장소 안(`docs/` 등)에 있다면 README에서 링크로 연결돼 있는가. 저장소 밖에 있다고 적혀 있으면 오래된 문구일 가능성이 큼 |
| 11 | 스크린샷/데모 이미지 | 화면이 있는 서비스인데 캡처가 하나도 없는가 (있으면 좋음, 특히 웹 서비스는 관례상 거의 필수) |
| 12 | 라이선스 | 오픈소스로 공개할 프로젝트면 필요, 학교 과제면 선택사항 |
| 13 | 뱃지·목차 | 있으면 보기 좋지만 필수는 아님 (README가 길 때만 목차가 의미 있음) |

## 진행 순서

### 1단계 — README 읽기
대상 프로젝트의 README.md를 읽는다.

### 2단계 — 실제 코드와 대조하기
아래를 확인해서 README 내용이 "지금 실제로 맞는 말인지" 검증한다. 이 단계가 이 스킬의 핵심이다 — README만 읽고 판단하면 안 되고, 반드시 실제 코드를 확인해야 한다.

- `Glob`/`Grep`으로 실제 폴더·파일 구조를 뽑아, README의 "프로젝트 구조" 섹션과 다른 부분이 있는지 비교
- README가 "OO 연동 예정"이라고 했는데, 관련 코드(예: DB 클라이언트, API 호출)가 이미 존재하면 → 이미 완료된 것이므로 문구가 오래됨
- README에 적힌 화면 경로(`/foo/[id]` 등)가 실제 라우트 파일 구조와 일치하는지 확인
- `docs/`, `PRD`, `API명세`, `보안점검` 같은 문서 파일이 저장소 안에 실제로 있는지 확인 (있는데 README가 "저장소 밖에 있다"고 하면 오래된 것)
- git 저장소라면 로드맵에 적힌 마지막 단계 이후에도 커밋이 있었는지(`git log`) 봐서, 로드맵이 실제 최신 진행 상황까지 반영됐는지 확인
- 스크린샷 파일(`.png`, `.jpg`, `.gif` 등)이 저장소나 README 안에 실제로 참조돼 있는지 확인

### 3단계 — 프로젝트 성격 구분
사용자에게 (또는 맥락에서) 이 프로젝트가 **과제 제출용**인지 **포트폴리오/오픈소스 공개용**인지 확인한다. 이미 대화 맥락에서 알 수 있으면 물어보지 않아도 된다.

- 과제 제출용: 1~10번이 핵심, 11~13번(스크린샷·라이선스·뱃지)은 있으면 좋지만 없어도 크게 문제 없음
- 포트폴리오/오픈소스 공개용: 11번(스크린샷)은 사실상 필수, 12번(라이선스)도 챙기는 게 좋음

### 4단계 — 점검 결과 보고 (여기서 멈추고 사용자 확인받기)
아래 표 형식으로 정리해서 사용자에게 먼저 보여준다. **이 단계에서 아직 파일을 고치지 않는다.**

```
| 항목 | 상태 | 비고 |
|------|------|------|
| 제목/한줄소개 | ✅ 있음 | |
| 라이브 링크 | ✅ 있음 | |
| 기술 스택 | ⚠️ 오래됨 | "OO 연동 예정"이라고 되어있는데 이미 구현됨 |
| 프로젝트 구조 | ⚠️ 오래됨 | 실제론 lib/requests.ts가 생겼는데 README엔 없음 |
| 로드맵 | ❌ 없음/부족 | 배포·보안점검 이후 단계가 반영 안 됨 |
| 스크린샷 | ❌ 없음 | (과제용이라 필수는 아니지만 있으면 좋음) |
```

그리고 짧게 총평 한 줄: "과제 제출 기준으로는 [충분함/부족함], 포트폴리오 기준으로는 [스크린샷 등] 보강하면 좋겠습니다." 같은 식으로.

### 5단계 — 사용자 승인 받고 수정
사용자가 "고쳐줘" 또는 특정 항목만 골라서 승인하면, **그 프로젝트의 실제 현재 상태에 맞게** 채워 넣는다. 지어내지 말고, 2단계에서 실제로 확인한 사실만 반영한다.

수정 시 반드시 지킬 것:
- **비밀값 절대 금지**: API 키, DB 접속 문자열, 비밀번호, 토큰 등 실제 값은 README에 어떤 형태로도 넣지 않는다. 환경변수 안내는 변수 **이름**만 예시로 보여준다 (`NEXT_PUBLIC_SUPABASE_URL=your-project-url` 처럼).
- **git 저장소라면 커밋 전에**: `git fetch`로 원격 상태를 확인하고, 다른 사람/다른 세션이 같은 파일을 먼저 바꿨는지 본다. 바뀌었으면 받아서 병합한 뒤 진행하고, **강제 push는 하지 않는다.**
- 수정 후 커밋 전 **최종 비밀값 재검사**(grep으로 API 키 패턴, 토큰 패턴 등 확인)를 한 번 더 한다.
- 실제로 push까지 할지는 사용자에게 확인한다.

### 6단계 — (선택) 실제 반영 확인
push했다면, 가능하면 실제 배포된 페이지나 GitHub 렌더링 결과를 열어서 의도대로 보이는지 확인한다 (특히 체크박스·표 같은 마크다운은 텍스트로만 보면 놓치기 쉬우니, 가능하면 브라우저로 실제 렌더링을 확인).

## 말투 안내

사용자는 코딩·GitHub을 배우는 중일 수 있다. "JSON", "CI", "머지 충돌" 같은 용어를 쓸 때는 짧게 풀어서 설명하고, 표·이모지를 활용해 한눈에 보이게 정리한다. 어려운 개념을 설명할 땐 실생활 비유(식당의 홀/주방 비유 등)를 써도 좋다.
